1. MEDIUM src/receipt_chain/record.rs:847 — `fold_in_v2_epoch` hashes `base ‖ schema ‖ epoch_json` with no length prefix and no domain tag.
   - `schema` is variable-length and sits directly next to the JSON bytes, so the boundary between them is ambiguous.
   - An attacker who controls both `schema` and the epoch JSON can move bytes across that boundary and get the same chain hash.
   - A v2 record's `v2: None` path returns `base` unchanged, so a v1 record and a v2 record can be told apart only by the hash input itself.

2. MEDIUM src/receipt_chain/record.rs:382-386 — the admission frame's `mixed_hash` is plain `blake3::hash(payload_hash ‖ meta_json)`.
   - It is un-keyed and has no domain tag, and it uses the same primitive as the other chain hashes at record.rs:847 and frame.rs:366.
   - `meta_json` is serde output of a tuple, which is fine today. It is not canonical against struct or field changes, so a serde or version change silently changes every hash.
   - The `.unwrap()` at line 382 is currently infallible, but it is a panic site on a public fn.

3. LOW src/receipt_chain.rs:363-367 — `obligations_created.len() as u32` and `.sum::<u32>()` can truncate or overflow.
   - The `as u32` casts truncate silently.
   - The `u32` sum panics in debug builds and wraps in release builds.
   - Items come from deserialized records, so a record with 2^32 obligations would get a wrong `obligation_count` and a wrong andon level.
   - This is only practical with a huge input.

4. LOW src/receipt_chain.rs:614 — `.expect("promoted=true ...")` guards an invariant that holds only if every constructor honours it.
   - If a deserialized or externally built builder sets `promoted` without `explicit_ceiling`, `build()` panics instead of returning `CoreError`.
   - I did not confirm the field is private, so this depends on field visibility.

5. LOW src/law.rs:544 and src/law.rs:604 — `unreachable!` on an external `#[non_exhaustive]` enum.
   - A dependency bump that adds a `ReasonerLimit` variant would make the reasoner panic at runtime, because the census code hits `unreachable!` when that variant appears.
   - Failing loudly is the stated intent, but a panic in a library is not an `Err`.

6. LOW src/receipt_chain.rs:983 — `check_chain_linkage` compares hex strings case-sensitively.
   - Records are not checked for canonical lowercase hex.
   - A producer that emits uppercase hex can only be rejected as a linkage mismatch, never normalised.
   - No exploit found, because the recompute stage presumably compares in bytes.

1. **Medium** `engine_load.ex:321-330` — `[:graphlaw_ex, :engine, :admit]` is emitted with raw `:telemetry.execute/3`, bypassing `Telemetry.emit/3`. The moduledoc says every emitter goes through `emit/3`, so nothing unredacted reaches a handler. The metadata carries a caller-influenced `code` and `digest`, and nothing redacts or filters them. A refusal path that passes a non-atom or long value as `code` (or a long non-sha `digest`) reaches handlers in the clear. The event also has no `duration`, so engine load time is unobservable.

2. **Medium** `telemetry.ex:307-310` — `classify(_) -> {:ok, nil}` treats any non-tuple result as success. A capability that returns bare `:error`, `{:error, reason}` (which goes to `:refused`/nil, so is fine) or a `nil` or atom failure is counted as `outcome: :ok`. Success-rate metrics are inflated, and an unexpected return shape is silently hidden.

3. **Medium** `host.ex:497-505` vs `telemetry.ex:307-309` — the `:outcome` vocabulary is inconsistent across events. Admit uses `:ok | :refused`. Host call uses `:ok | :refused | :error`, where `:error` means a `%Refusal{}` and `:refused` means a non-`ok:true` response with a nil code. The engine load event uses `:admitted | :refused`. A reporter keyed on `outcome` cannot aggregate these, and `:refused` means a different thing in admit than in host.

4. **Low-Medium** `telemetry.ex:181-182`, `catalog.ex:66` — `source_digest` is `:plain` and only length-checked (at most 128 bytes). It is never validated as a `blake3:` digest. A caller can pass an arbitrary string of up to 128 bytes (a name, a request fragment), and it passes verbatim into metadata and the default logger. It is also a per-law-content value, so any metrics reporter that uses it as a tag gets unbounded cardinality. The catalog does not mark it as non-tag-safe.

5. **Low-Medium** `telemetry.ex:62-66` — `op` is `:plain` and any binary of at most 128 bytes passes in the clear. `admit/3` accepts any binary `op`, so a dynamically built op name becomes unbounded tag cardinality. The code has no allowlist of ops.

6. **Low** `host.ex:409,549,860` with `telemetry.ex:169` — the recycle `reason` `{:instance_exit, exit_tag(reason)}` collapses to `%{tag: :instance_exit}`. The exit tag, which is the diagnostic part, is lost from telemetry. Nothing else in the recycle event preserves it (only a count and the wasm sha256).

7. **Low** `telemetry.ex:219-223`, `catalog.ex:173,189` — every `emit/3` and `log_level/1` call does `Enum.find` over a freshly built 8-element catalog list. It is cheap, but it sits on the hot path of every admit and host call (3 emits per span). Compile-time maps keyed by event would remove it.

8. **Low** `telemetry.ex:243-273` — the stop and exception emits are inside the `try`. If `emit/3` itself raised (for example `Catalog` misuse or a bad metadata term inside `redact/1`), the catch would emit a bogus `:exception` and re-raise a telemetry error as the call's failure. `redact/1` is documented as never raising, but `Map.new` on a map with odd keys is the only protection, and handlers are isolated by `:telemetry`. 9. **Low** `host.ex:328,823,843` — the retry warnings are plain Logger strings with no metadata and no telemetry event. Engine-unavailable retries and recycle failures have no counter, so an alert can only grep logs.

MEDIUM wasm/src/ffi.rs:260-266 (`pack_response`) — When the outstanding cap is saturated, every response is a handle to one shared zero-budget buffer. The first `gl_free` of that pointer reclaims it, and the host's other handles to the same pointer then dangle. A later `gl_free` is ignored safely, but the host still reads freed linear memory through those handles. The shared buffer can also be reallocated to another publisher at the same address. Failure scenario: a host with N concurrent saturated calls gets N identical `(ptr, len)` pairs and frees the first. Reads through the remaining N-1 handles return garbage or another call's bytes. This is a use-after-free by the host that the guest invites. The side table protects the guest's heap, not the host's reads.

MEDIUM wasm/src/ffi.rs:164-175 and 217-232 — The budget counts requested bytes (`n`, `response.len()`), not allocator capacity or the `BTreeMap` node overhead. Nothing handles allocation failure. `vec![0u8; n]` and `live().insert` abort on OOM, and with `panic=abort` that is a trap. Failure scenario: the 16 MiB cap assumes linear memory can always grow. If the wasm memory maximum is lower, or DuckDB has already consumed memory, `gl_alloc(16 MiB)` traps the instance instead of returning null. That breaks the documented "null, never a trap" contract in the `gl_alloc` doc comment (ffi.rs:262-266). It would be sounder to use `Vec::try_reserve_exact`.

LOW wasm/src/ffi.rs:199-212 (`call_buf`) — If `graphlaw::abi::call` panics, the request buffer was already reclaimed and the budget is never released. Under `panic=abort` this is moot because the instance is dead. Under any unwind configuration, such as native tests without the wasm profile or a `catch_unwind` host, the request buffer's budget leaks permanently. The code does not enforce abort semantics, and `[profile.wasm]` is the only place that sets `panic = "abort"`. A plain `cargo build --target wasm32-wasip1 --release` unwinds through the `extern "C"` boundary, which is UB or an abort depending on the toolchain.

LOW wasm/src/ffi.rs:253-265 — The pointer is packed as `(ptr as u64) << 32 | len`. The only protection is the `cfg` on the exports, and there is no `const` assert on `size_of::<usize>() == 4`. LOW wasm/src/ffi.rs:260 — `declared` uses `u32::try_from(...).unwrap_or(u32::MAX)`.
